## D1. 製品名は `sshboard`・発見される語は名前の外に置く — 【決定・2026-08-25】

**Why:**

- **`dbboard` と同じ形です。**`db` + `board`、`ssh` + `board`。
  board ブランドは元々「技術名 + board」であり、ブランドと発見性の二者択一ではありません
- SFTP も exec も、**全部 SSH の上**です。統合後の名前としては SSH が正確です
- 世界の開発者が探す語（`mcp sftp client` / `mcp ssh terminal`）は**製品名に入れません。**
  description / topics / README 冒頭 / MCP レジストリ登録に置きます。
  **実際に探される主経路は MCP のレジストリと一覧サイト**で、そこは description で引かれます
- 後から他の「盤」を足すときにブランドが効きます

**How to apply:** PRD §8「発見される語をどこに置くか」の表に従う。リポ作成時に description と topics を必ず埋める。

## D2. Phase 1 は読み取り専用 — 【決定・2026-08-25】

アップロード・上書き・削除・リネーム・移動・パーミッション変更・転送キュー・
サービス再起動・パッケージ操作・承認 UI を Phase 1 に入れない。

**Why:**

- **解こうとしている痛みが 100% 読み取りです。**障害調査・メール設定調査・提案、どれも読むだけ
- 危険がほぼゼロになるので、**稼働中の本番サーバーを初日から対象にできます**
- 実装量が大きく減ります。転送キュー・上書き衝突・削除確認・承認待ちの機構が丸ごと消えます
- `dbboard` が read-only MCP でこの形を先に成立させています

**How to apply:** Phase 1 の MCP ツールに、サーバー側の状態を変えるものを 1 つも作らない。

## D3. AI に任意コマンドを渡さない — 【D29 が条件つきで覆した・2026-08-30】

> **この決定は D29 で条件つきに覆されています。**
> AI にコンソールを渡します。ただし**排他ロックと停止ボタン**が付きます。
> **`run_command(cmd)` を作らない部分は生きています** — 渡すのは
> 「人の見ていない所で 1 行実行して返る口」ではなく、**人が見ていて止められる対話コンソール**です。

`run_command(cmd: string)` を作らない。用途ごとの読み取りツールと、
許可リスト方式の `run_readonly` だけを出す。

**Why:**

- `run_command` を 1 つ置けば全部できる。**だから危険**。
  破壊的操作を防ぐ手段が「使わない約束」しか残らない
- **約束は手順書であって、ゲートではない。**忘れた瞬間に穴が開き、
  相手はサーバーなので気づくのは壊れた後
- 許可リストなら**危険なコマンドは呼びようがない**。構造で防げる

**How to apply:**

- 引数で任意の文字列をシェルへ渡す MCP ツールを 1 つも作らない
- `run_readonly` の許可リストは既定を最小にし、実際に必要になったものだけ足す
- **GUI（人）の側は制限しない。**制限するのは AI の口だけ

### 追記（2026-08-27）— 許可リストは推測で書かず、**実測で育てる**

実物の画面を見た人から「決まったコマンド一覧を実施するボタンに見える」と指摘が出た。
**D3 は撤回しない。**ただし、既定の許可リストを**推測で書かない**ことを足す。

**Why:** いま誰も、実務でどのコマンドが要るかの一覧を持っていない。
**推測で書けば必ず外す。**多すぎれば D3 の意味が消え、少なすぎれば作業が止まる。

**How to apply:**

1. **既定は最小から始める。**用途別の 13 ツールで届く範囲は、そちらを使う
2. **拒否を機械が残す。**許可リストに無いコマンドを AI が呼んだら、
   - **帯へ出す**（人がその場で「いま何が足りなかったか」を見る）
   - **追記専用のファイルへ残す**（時刻・要求されたコマンド・呼んだ側）
   - **接続先と引数の中身を残さない**（PRD §8）。残すのはコマンド名と、拒否した事実
3. **足すのは人。**許可リストは設定ファイルで、**追加は差分として履歴に残る**
4. **AI が代筆しない。**「これも足しておきますね」をやらない。
   足りなかった記録は機械が出すが、**足す判断は人**（product-baseline §27）

**これを止めるべき条件:** 許可リストへの追加が週に何度も発生して作業が止まる場合。
そのときは「許可リストをやめて任意コマンドを渡す」を再検討する。
**ただし、そのときも `run_command` を無条件で開けるのではなく、
「何が実際に必要だったか」の実測が手元にある状態で判断する。**

**実装は Phase 1。**`run_readonly` は Phase 1 のツールであり、
**Phase 0 が通らないうちに書き始めない**（CLAUDE.md）。

### 追記（2026-09-01）— 実装した。**引数のスロットを作らなかった**

`sshboard-readonly` crate ＋ `Engine::run_readonly` ＋ MCP の
`run_readonly` / `list_readonly_commands` として入れた。テスト 31 本。

**AI が渡せるのは識別子だけ。**`run_readonly { command_id }` の 1 引数で、
**パスも引数も渡せない。**走るのは人が `readonly.toml` に書いた文字列そのもの。

**Why（引数を作らなかった理由）:** 引数のスロットは、そこが注入面になる。
`tail {path}` を許した瞬間、`path` に何が入るかは許可リストの外側の話になり、
「危険なコマンドは呼びようがない」が「危険な引数は渡しようがある」に変わる。
**ファイルを読む用途は `read_file` / `list_directory` で届く**（D3 の 1 番目）。
**実測でここに当たってから**、引数の形を決める（YAGNI）。

**正直に書いておくこと:** **製品は「本当に読み取り専用か」を検証できない。**
`uptime` と `rm -rf /` を機械が見分ける方法は無い。この仕組みが守るのは
「AI が文字列を組み立てられない」ことだけで、**安全を決めるのは書いた人**。
名前が `run_readonly` であることは、その保証を意味しない。

**置き場所:** `readonly.toml` と `readonly-refused.log` は
**接続一覧と同じディレクトリ**。2 か所に散らすと、人が「どちらを編集したのか」を
追えなくなる（D25 で実際に食い違った）。

**断り方:** 一覧に無い識別子は、**サーバーへ届く前に**断る
（`NotConnected` より先に `NotAllowed` を返す）。断ったら帯へ 1 行出し、
`readonly-refused.log` へ 1 行追記する（時刻・呼んだ側・要求された識別子の 3 列。
**接続先も引数も残さない**）。**記録できなくても断る。**
「記録できないから通す」は、ここで一番やってはいけない転び方。

**既定は空のまま出した。**`readonly.toml` の雛形も同梱していない
（コメントアウトした例でも「これを足せ」の示唆になるため・D3 追記の 4 番目）。

**新しい直接依存: `chrono` 0.4**（baseline §2 / §12）。
拒否の記録に RFC 3339 の時刻を付けるため。**すでに Cargo.lock に居たもの**
（0.4.45・tauri 経由）を直接依存へ上げただけで、**供給元は増えていない。**
代替として自前で暦を書く案は採らなかった — 3 列のためにうるう年の計算を持つのは負債。

### 追記（2026-09-02）— 用途別ツールを 5 本。**引数は例外なく囲う**

`disk_usage` / `process_list` / `network_listen` / `service_status` / `read_log`。
D3 の「必要な操作は用途別ツールか `run_readonly` に足す」の、用途別の側。

**`service_status` と `read_log` は引数を取る。**これは `run_readonly` で作らなかった
注入面そのものなので、扱いを先に決めた。

- **コマンドを組み立てるのは製品側**（`sshboard-engine` の `probes`）。AI は値だけ渡す
- **引数は例外なく単引用符で囲う**（`sshboard-ssh` の `quote`）。
  **「英数字だけなら素通し」を作らない。**判定を 1 つ間違えたら終わりで、
  間違いは「動いてしまった」形で現れる。囲うのは安く、外すのは高い
- `--` を置き、**`-` で始まる値をオプションとして読ませない**
- **返ってこないコマンドを作らない。**`systemctl status` は既定でページャへ流すので、
  端末の無い `exec` では返らない（`--no-pager`）。**踏む前に潰した**
- **落ちる先を用意する。**`ss` の無い機械は実在するので `netstat` へ落ちる
- **書き込む語が混ざっていないことをテストで固定**（`tests/probes.rs`）

**引数の検査はサーバーへ行く前に済ませる。**空のサービス名で `systemctl status` を
打つと**全ユニットが返る** — 「押したのに違うものが出る」を作らない。

MCP のツールは 21 → 26 本。テスト 22 本（シェル引用 8・組み立て 14）。

### 追記（2026-09-02・続き）— 残り 3 本。**Phase 1 の読み取りツールが揃った**

`search` / `runtime_versions` / `stat` を足し、**PRD の一覧が全部 ✅ になった**（29 本）。

- **`search` は深さと件数の両方を切る。**`/` から探されたら返ってこない。
  `head` で止めるので `find` も途中で終わる（SIGPIPE）。
  中身の検索は `-I` でバイナリを飛ばす（**混ぜると端末が壊れる**）
- **`runtime_versions` は `command -v` で在るものだけ尋ねる。**
  入っていないことは異常ではない。**「エラーが出た」と返すと、AI は原因を探しに行く**
- **`stat` は権限を 8 進数 4 桁の文字列で返す**（`0644`）。`33188` を見せられても人は読めず、
  数値で返すと先頭の 0 が落ちる。**「なぜ読めないのか」は、たいてい権限が答える**

**`grep` のフラグも `df` と同じくまとめなかった**（`-rnI` ではなく `-r -n -I`）。
帯に出て人が読むので、何が効いているか見て分かる方に寄せた。
**この判断は 2 回とも、テストが先に落ちて気づいた** — `contains("-P")` /
`contains("-I")` が、結合したフラグに当たらなかった。

**`FileFacts` は serde を持たない。**`sshboard-ssh` は serde に依存しておらず
（`DirEntry` も同じ）、**JSON にするのは MCP の仕事**。依存を増やさずに済ませた。

`stat` は**手元のテスト用サーバーへ実際に繋いで確かめた**（実地テスト 2 本）。

## D4. ファイルと端末を 1 製品にする — 【決定・2026-08-25】

初版は `sftpboard` / `sshboard` の 2 製品として起草したが、**統合に変更した。**

**Why:**

- **用途が両方を同時に要求する。**障害調査はログ（ファイル）＋ プロセス・サービス（コマンド）、
  メール設定調査は設定ファイル（ファイル）＋ `postconf -n`・listen ポート（コマンド）。
  **片方だけでは終わらない**
- **決定打は MCP の登録。**2 製品だと利用者は MCP を 2 つ登録し、接続先リストを 2 か所で保守する。
  **「片方にはホストを足したが、もう片方に足していない」が必ず起きる。**
  Phase 1 が両方とも読み取り専用である以上、接続層を分ける利益が無い
- SSH 1 本の上で `sftp` サブシステムと `exec` を使い分けるだけになり、接続層はほぼ同じ
- インストーラも 1 つで済む

**How to apply:**

- **1 アプリ 2 画面。1 画面にしない。**既定はファイル 2 ペイン、ターミナルはタブ
- 副ユーザー（従来の慣習でないと作業できない担当者）に端末を覚えさせない
- 分離が必要になる証拠が出たときだけ分ける。**今は証拠が無い**

## D6. SSH ライブラリは `russh` — 【決定・2026-08-27】

`russh`（純 Rust）＋ `russh-sftp` を採る。`ssh2`（libssh2 バインディング）は採らない。

**カタログではなく、実機で決めました。**（Issue 002 の「実行結果」に生の値があります）

**実機で分かったこと:**

- **両方とも通りました。**1 本の接続の上で `exec` と `sftp` の `ls` が、どちらでも動いた
- **判断材料 1（古い鍵交換方式・暗号方式）は決め手になりませんでした。**
  対象 13 台は OpenSSH 8.7 / 9.9 で、`diffie-hellman-group1-sha1` も `3des-cbc` も
  `ssh-dss` も 1 台も出していない。**古さの問題は、この環境には存在しない**
- したがって**判断材料 2 と、それ以外の条件で決めることになりました**

**Why（`russh` を採る理由）:**

- **house の実績がある。**dbboard が本番で使っている（ADR-0069・SSH ローカルフォワード）。
  **D5 の boardkit へ引き上げられる**のは同じ側だけ
- **純 Rust。**`ssh2` は libssh2 と OpenSSL の C 依存を引く。
  探り棒のビルドで実測したが、`vendored-openssl` は source から OpenSSL を建てるため遅く、
  Windows の CI では perl / nasm が要る。**配布物を 1 バイナリで出す方針（D8）とも噛み合わない**
- **dbboard の ADR-0034（`aws-lc-rs` を入れない）と揃えられる。**
  `russh` の既定は `aws-lc-rs` を引くので、`default-features = false` ＋ `ring` にする。
  **採用したら `cargo tree` で毎回確かめること**

**採らなかった `ssh2` の良かった点（記録として残す）:**

- **SFTP を内蔵している。**`russh` は別 crate（`russh-sftp`）が要る
- **成立した方式を教えてくれる**（`Session::methods`）。`russh` にこれが無いので、
  「実際にどの暗号で繋がったか」を出したいときは自前で持つ必要がある

**これを止めるべき条件:**

- `russh-sftp` が保守されなくなる、または Phase 1 で要る操作を持っていないと分かったとき
- **そのときは `ssh2` へ戻すのではなく、まず `russh-sftp` を代替できるかを見る。**
  C 依存を引き込む判断は、それでも駄目だったときに改めて行う

**How to apply:**

```toml
russh = { version = "0.63", default-features = false, features = ["ring", "flate2", "rsa"] }
russh-sftp = "2"
```

- **ホスト鍵の検証を必ず入れる。**`russh` の `check_server_key` は既定で全部拒否する。
  **blind-accept を型で作れない形にする**（dbboard ADR-0069 と同じ扱い）
- **指紋を固定するときは、方式も一緒に記録する。**同じサーバーでも、
  成立したホスト鍵の方式が違えば指紋も違う（実機で踏んだ）

**Why:**

## D12. コード署名は初手では入れない — 【決定・2026-08-25】

**証明書は製品ごとではなく組織ごと**です。前提の訂正:

| | 単位 | 費用 |
|---|---|---|
| Windows（OV/EV コード署名） | **組織ごと**。同じ組織の何本でも署名できる | 年 55,000 円前後 + 鍵の保管（2023-06 以降、秘密鍵は FIPS 140-2 L2 以上のハードウェア必須） |
| macOS（Apple Developer Program） | **組織ごと** | 年 99 ドル |

**「1 製品あたり 55,000 円」ではありません。**3 製品でも合計は年 7 万円前後です。

それでも初手では入れません。**判断材料は利用者数であって、値段ではない**からです。
未署名でも動きます（Windows は SmartScreen の「詳細情報」→「実行」、macOS は右クリック→開く）。
**未署名で脱落する利用者が実際に出てから買います。**

## D15. MCP は 127.0.0.1 の Streamable HTTP で出す — 【決定・2026-08-26】

MCP のトランスポートを stdio ではなく、**アプリ自身が loopback に bind する
Streamable HTTP** にする。実装は `rmcp` の `transport-streamable-http-server`。

**Why:**

- **stdio の MCP は、クライアントがサーバーを起動する形になる。**
  Tauri の GUI プロセスの stdin/stdout を MCP クライアントへ渡す方法が無いので、
  stdio を選ぶと別プロセスを立てるしかない。それは D8「MCP はアプリ内蔵」と
  Issue 001「別プロセスを立てない」の両方に反する
- アプリ自身が listen すれば、**増えるプロセスは 0 本。**GUI と MCP が
  同じ Operation Engine・同じ 1 本の SSH を共有する形（PRD §4-1）を保てる
- `rmcp` 3.1.4 に該当のトランスポートがあり、自前で書く部分が無い

**How to apply:**

- **`127.0.0.1` にしか bind しない。`0.0.0.0` にしない。**テストで見張る
  （`the_mcp_port_is_bound_to_loopback_only`）
- **この口は認証を持っていない。**loopback でも、同じ端末の別プロセスからは叩ける。
  **Phase 1 で実際にサーバーを触るツールを載せる前に、トークンを必須にすること。**
  Phase 0 の `ping` は何も触らないので今は無害
- ポート番号の扱いは**まだ決めていない。**Phase 0 は 0 を渡して OS に選ばせている。
  Phase 1 で MCP クライアントへ登録する都合上、固定ポートか、
  実際の番号を設定ファイルへ書き出す形が要る。そこは実際に登録して決める

## D16. 帯が受け取るまで、MCP ツールの応答を返さない — 【決定・2026-08-26】

MCP ツールは、操作を帯へ載せ、**画面が受け取りを返してから**応答を返す。
期限内に返らないときは**ツールを失敗させる。**

**Why:**

- 応答を先に返すと、**AI が返答したあとに画面が追いつく**形になる。
  それは「人が見ている」ことにならない（PRD §4-2・Issue 001 の完了条件）
- 「たぶん出ているはず」で進めると、**画面が固まっていることに誰も気づかない。**
  見えないことが最大の危険（PRD §4-1）である以上、ここは best-effort にしない

**How to apply:**

- `Band::record` は配達票（`Delivery`）を返す。`Delivery::wait_acked` で待つ
- 期限切れ（`DeliveryOutcome::TimedOut`）を握り潰さず、ツールを失敗させる
- **画面をまだ開いていない（購読者 0）ときは待たない。**そこは「見えない」ではなく
  「見る人がいない」であり、別の話
- **「受け取った」の線は DOM に入るところまで。描画（`requestAnimationFrame`）を待たない。**
  WKWebView はウィンドウが前面に無いと rAF を止める。この製品は「人はエディタを見ていて、
  AI が裏で動く」使い方が普通なので、描画を待つ作りにすると**背面にした瞬間に
  MCP が全部失敗する。**2026-08-26 に実機で踏んだ

## D18. 接続情報は暗号化バンドルで受け渡す — 【決定・2026-08-27】

登録した接続を **1 つのファイルに書き出して人へ渡し、相手が読み込める**ようにする。
dbboard の **ADR-0038** と同じ形（`age` のパスフレーズ暗号 ＋ パスフレーズは別経路）。

**Why:**

- **`connections.toml` は、それ単体では別のマシンで役に立たない。**
  中身は OS ストアの参照名だけで（D11 / ADR-0013）、参照先が相手のマシンに無い
- **実務で一番手間なのがここ。**IP はフォルダ名、ログイン ID は別の表、鍵は `.ppk`、
  パスフレーズはさらに別。**揃えること自体が仕事になっている**（2026-08-27 に実測）
- **「安全のために分散させる」に実利が無い。**
  PC が取られた時点で終わりであり、**接続時にはどのみち 1 箇所へ集約される。**
  手元で散らしても攻撃者の手間が増えるだけで、守れてはいない
- バンドルが外へ出る点は、**パスフレーズ暗号 ＋ パスフレーズの別経路**で手当てする。
  これは dbboard で既に運用している形

**How to apply:**

- 拡張子は `.sshbx`。中身は `age` でパスフレーズ暗号化した JSON
- **パスフレーズはバンドルと同じ経路で送らない**（別経路で渡す）
- 読み込み時は、秘密を **OS ストアへ入れてから** `connections.toml` を書く。
  途中で失敗したら、入れた分を戻す（ADR-0038 と同じ順序）
- **ssh-agent を使っている接続は、鍵そのものがバンドルに入らない。**
  入るのは host / port / user と鍵のパスだけになる。**これは摩擦ではなく、
  agent へ委譲している（D11）ことの自然な帰結**
- **実装は Phase 1-A**（接続管理）。**Phase 0 が通らないうちに書き始めない**（CLAUDE.md）
- **D5 の boardkit 引き上げ候補。**dbboard に実装があるので、2 本目のここで
  実測の重複として引き上げる

**分かったうえで受け入れているリスク:**

- **バンドル 1 つで対象サーバー全部に入れる。**dbboard のバンドルに入るのは
  DB の URL やトークンだが、**sshboard のそれは SSH の鍵とパスフレーズになる**
- 受け入れる理由は上の Why のとおり。**分散させても守れないから**

## D19. `.ppk` は「検出して案内する」— 【D28 が覆した・2026-08-30】

> **この決定は D28 で覆されています。**変換の案内は製品から外しました。
> 前提としていた「読める Rust crate が実質無い」が**事実として誤り**で、
> 既に採用している `russh` 0.63（`ssh-key` 0.7）が PPK v2 / v3 を読めます。
> **拡張子で検出する実装だったことも害でした**（下の D28）。

PuTTY 形式（`.ppk`）の鍵は**自前で読まない。**
登録時に検出して、**OpenSSH 形式への変換手順を画面で案内する。**

**Why:**

- **実機の鍵が `.ppk` だった**（2026-08-27）。保守は Tera Term / WinSCP で回っており、
  鍵は `.ppk` で手元にある。**PRD §1 の副ユーザーは全員この状態**とみてよい
- **OpenSSH 系（`russh` / `ssh2`）は `.ppk` を読めない。**
  読める Rust crate も実質無い（2026-08-27 時点で確認）
- **自前で読むのは採らない。**鍵の形式を自前で解釈するのは事故のもとで、
  D7（ANSI を自前で書かない）と同じ理屈。**そこは本製品の価値ではない**
- **何もしない案も採らない。**「鍵が読めません」とだけ出すと、
  副ユーザーはそこで詰まる。**詰まる場所が分かっているのに黙るのは、道具として不親切**

**How to apply:**

- 鍵のパスが `.ppk` で終わる、または中身が PuTTY 形式のとき、
  **登録画面でその場で気づかせる。**接続を試みてから失敗させない
- 案内するのは変換コマンドと、**ssh-agent を使う道**の 2 つ:

  ```sh
  brew install putty          # macOS。Windows は PuTTY 同梱の puttygen
  puttygen <鍵>.ppk -O private-openssh -o <鍵>
  ssh-add --apple-use-keychain <鍵>
  ```

- **変換はアプリがやらない。**人の手元で 1 回やってもらう。
  秘密鍵を製品が書き出す経路を作らない（D11 / product-baseline §14）
- **実装は Phase 1-A**（接続管理）

**これを止めるべき条件:**

- 副ユーザーが変換で詰まる事例が実際に出たとき。
  そのときは「アプリが変換する」ではなく、**まず案内の文言を直す。**
  それでも駄目なら `.ppk` の読み取りを検討する

## D20. 昇格の資格情報を製品に持たせない。サーバー側で読めるようにする — 【決定・2026-08-27】

`/var/log` がログインユーザーで読めなかった（実機・2026-08-27）。
PRD §0-2 の主用途は「障害調査 ＝ ログを読む」なので、**このままでは主用途が成立しない。**

**`su -` / `sudo` のパスワードを製品に持たせない。**
代わりに**サーバー側**で、そのログを読めるようにしてもらう。

**Why:**

- **D11 の真逆になる。**「持たなければ守らなくてよい」で作ってきたものが、
  **root のパスワードを持つ**ことになる
- **バンドル（D18）に root のパスワードが入る。**ファイル 1 つで全サーバーの root になる
- `su` は対話的で、**パスワードを流し込む実装そのものが事故のもと**

**How to apply（サーバー側で 1 回・root が行う）:**

**B-1（推奨）— ファイルの ACL / グループで読ませる。sudo を使わない**

```sh
setfacl -m u:<利用者>:r /var/log/<読ませたいログ>
```

**sudo が一切出てこない。D2（AI に sudo を渡さない）がそのまま守れる。**
製品から見ると「読めるファイルが増えた」だけになる。

**B-2（B-1 が使えないとき）— sudoers に読み取り専用コマンドだけ NOPASSWD で置く**

```
<利用者> ALL=(root) NOPASSWD: /usr/bin/tail -n * /var/log/<ログ>
```

- **パスワードは要らない**（NOPASSWD）
- **許可リストがサーバー側の sudoers にある。**アプリが約束するのではなく **OS が拒否する。**
  D3 の「約束は手順書であって、ゲートではない」と完全に一致する

**採らない案:**

- **`su -` のパスワードをアプリ（または OS ストア、またはバンドル）に置く。**上記の Why のとおり
- **AI に無制限の sudo を渡す。**D2 / PRD §5 のまま変えない

**これを止めるべき条件:**

- 対象サーバーの運用で ACL も sudoers も触れない場合。
  そのときは**「そのサーバーではログを読まない」を選ぶ。**
  **パスワードを持つ側へは倒さない。**

## D21. AI は**ローカルの設定**を書ける。リモートへの書き込みは引き続き作らない — 【決定・2026-08-27】

MCP に `register_connection` を作る。**接続の登録を AI ができるようにする。**

**Why:**

- **接続情報を揃えること自体が仕事になっている**（実測・2026-08-27）。
  IP はフォルダ名、ログイン ID は別の表、鍵は `.ppk`。
  **人が画面に打ち込む前提だと、その手間が残る**
- この製品は AI に指示して動かすもの（PRD §4）。**登録だけ人が手で打つのは筋が通らない**

**線引き（ここが要点）:**

| | AI ができること |
|---|---|
| **ローカルの設定ファイル** | **書ける**（接続の登録） |
| **リモートサーバー** | **1 バイトも書けない。**D2 / CLAUDE.md 禁止事項 2 は変えていない |

D2 が禁じているのは**リモートへの書き込み**（アップロード・上書き・削除・リネーム・
移動・パーミッション変更・サービス再起動・パッケージ操作・sudo）です。
**接続の登録はそこに当たりません。**

**How to apply:**

- **秘密を引数に取らない。**パスフレーズもパスワードも項目にない。
  鍵は ssh-agent か、鍵ファイルのパスだけ（D11）。
  **ツール定義に秘密の引数が生えていないことをテストで見張る**
- **帯には識別子だけを載せる。**帯は画面に出るので、ホスト名を載せると
  画面の写真に接続先が写る（PRD §8）
- **黙って上書きしない。**同じ識別子が既にあれば失敗させる。
  上書きすると、人が登録したものが消える
- 識別子は英数字と `.` `_` `-` だけ。ファイルにも帯にも出るため

**これを止めるべき条件:**

- AI が意図しない接続を登録する事例が出たとき。
  そのときは**削除を AI に渡さない**まま、登録に人の承認を挟む形へ変える。
  **リモートへの書き込みを開ける方向へは倒さない**

## D22 — Phase 1 にリモートへの書き込みを入れる（D2 を覆す）

**決めたこと**

**D2「Phase 1 に書き込みを入れない」を覆し、SFTP のアップロードを入れる。**
ただし **AI が書ける場所を、接続ごとの「書き込み許可ディレクトリ」に閉じ込める**。
既定は空 ＝ **設定していない接続で AI は 1 バイトも書けない**。
**囲いは AI の口にだけかかる。人（GUI）は従来どおり制限しない**（PRD §3）。

入れたのは **上げる・ディレクトリを作る**だけ。
**消す・動かす・名前を変える・権限を変える・サービスを再起動する・sudo は入れない**
（Phase 2 のまま。MCP のツール一覧をテストで見張っている）。

**根拠**

- 運用者の実際の用途が「VPS へプロダクトを上げる」で、**読み取りだけでは 1 ミリも楽にならない**。
  PRD §0-2 が挙げた 3 用途がすべて読み取りだったのは、**上げる用途を数えていなかったから**
- 危険を「使わない約束」で防ぐのは手順書であってゲートではない（PRD §3）。
  **書ける場所そのものを列挙**すれば、囲いの外は**呼びようがない**。D3 と同じ考え方
- 囲いを設定するのは**画面を見ている人だけ**。
  **AI が登録した接続の許可は常に空**にしてある。自分で登録して自分に許可を出せるなら囲いは無意味

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| 書き込みを一切入れない（D2 のまま） | 主要な用途が成立しない。**道具として使われないものは安全でもない** |
| 書き込みのたびに人が承認する | 1 回の配置で数十ファイル上がる。**承認が儀式になる**（押すだけになったゲートは無い方がまし） |
| 許可を「危険なパスの拒否リスト」で作る | 漏れが必ず出る。**許可リストは漏れても閉じる側に倒れる** |
| 人にも同じ囲いをかける | 普通の SFTP クライアントとして使えなくなる（PRD §1 の副ユーザーを切り捨てる） |

**これを止めるべき条件**

- 囲いの外への書き込みが 1 件でも通ったとき。**そのときは書き込みごと落とす**
- 「許可ディレクトリを広げてくれ」と AI が繰り返し言い、人が根拠なく広げ始めたとき。
  囲いが形骸化している。**用途ごとに接続を分ける方へ倒す**

**実行状況**

実装済み（`crates/sshboard-ssh/src/write_scope.rs` / `session.rs`）。
実機（`tools/test-server`）で、囲いの外を断ったあと**サーバー側の一覧を見て
本当に届いていないこと**まで確認している。

## D23 — MCP にトークンを必須にする

**決めたこと**

`127.0.0.1` の MCP へ、**起動ごとに変わる合言葉を必須にする**。
`Authorization: Bearer <token>` が合わないリクエストは、**initialize すら通さず 401**。
合言葉は OS の乱数から作り、**ファイルには保存しない**（アプリを閉じると無効）。

**根拠**

- `http.rs` 自身が最初から「**Phase 1 で実際の操作を載せる前にトークンを必須にすること**」
  と書いていた。**D22 で書き込みを載せた今回がその時点**
- loopback にしか bind していないが、**同じ端末の別プロセスからは叩ける**。
  読むだけなら実害が小さかったが、いまは**他人のプロセスがあなたの VPS へファイルを置ける**
- 合言葉は端末へ出さない（`product-baseline` §14）。**画面に出して、人が写して貼る**

**どこへ置くか — 一度 OS 資格情報ストアにして、戻した**

最初は起動ごとに作り捨てにしたが、**人が毎回 `claude mcp add` をやり直すことになる**
（面倒を減らす道具が新しい面倒を足す）。そこで OS 資格情報ストアへ置いた。
**それも外した。実測で毎回承認ダイアログが出た。**

macOS のキーチェーン ACL は**バイナリに紐づく**。開発中はビルドのたびに別の
バイナリになるので、「常に許可」を押した相手と次に起動する相手が別物になる。
署名すれば固定されるが、**署名は後回しにしている**（D12）。

**結論**: OS 資格情報ストアは「**リモートを開ける秘密**」の場所（鍵のパスフレーズ・D11）。
MCP の合言葉は **loopback の取っ手**で、露出度は `connections.toml` と同じ。
**同じ置き場所・同じ権限（0600）**に置く。`SSHBOARD_MCP_TOKEN` があればそれを優先する。

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| loopback だから不要 | 同じ端末の別プロセスを防げない。**これから書き込みが載る** |
| URL のパスに合言葉を埋める | シェルの履歴とプロセス一覧に残る |

- 合言葉の受け渡しが面倒で、人が MCP を使わなくなったとき。
  そのときは**貼る手間を減らす**方へ倒す（合言葉を弱くする方へは倒さない）

**実行状況**

実装済み。合言葉なし・違う合言葉・正しい合言葉の 3 通りをテストしている。
**実物のアプリでも** 401 / 401 / 200 を確認した。

## D24 — 同じ相手へ何度も探りに行かない

**決めたこと**

ホスト鍵を確かめるための接続（**繋いで、鍵を見て、信用できなければ認証せず切る**）を、
**同じ相手へ繰り返さない**。指紋は 1 回取って使い回し、人が確かめて登録した後は固定した指紋で繋ぐ。

**根拠**

**実測で落ちた。**OpenSSH 9.8 以降の `PerSourcePenalties` は
「認証を試みずに切れた接続」を罰する。手元のテスト用サーバーのログにこう出た。

```
drop connection #8 ... penalty: connections without attempting authentication
```

sshboard の**ホスト鍵検証そのものが、この罰の対象になる**（D6 の要）。
テスト用サーバーでは `PerSourcePenalties no` で切ったが、
**実機では切れない。**相手の設定だから。

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| 認証まで進めてから鍵を判断する | **信用していない相手へ鍵を出す**ことになる。本末転倒 |
| 罰に当たったら黙って再試行する | 罰が伸びる。**相手から見れば総当たりと区別が付かない** |

**これを止めるべき条件**

- 実機で罰に当たった事例が出たとき。そのときは**待ち時間と理由を画面に出す**
  （黙って再試行する方へは倒さない）

**実行状況**

テストは指紋を 1 回だけ取って使い回す形になっている（`OnceCell`）。
**製品側の連打防止はまだ入っていない。**Phase 1 で入れる。

## D25 — 接続は複数持てる。ただし **1 本残らず画面に出す**

**決めたこと**

**同時に開ける接続を 1 本に制限するのをやめる。**WinSCP のようにタブで並べ、
切らずに次へ移れるようにする。

**代わりに、開いている接続は 1 本残らず画面のタブに出す。**
数も、どれが動いているかも、常に見える。

**根拠**

- 運用者は**複数台を行き来する**。1 台ごとに切って繋ぎ直すのは、道具として成立しない
  （実際に「いちいち切断しないと他につながりません」と言われた）
- PRD §4-1 が禁じているのは「**裏で見えない**セッション」であって、複数であること自体ではない。
  **危険なのは見えないことで、本数ではない。**タブに全部出るなら、その危険は無い
- 1 本しか持てない設計は、**AI が繋いでいる間、人が何もできない**という別の問題も作っていた

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| 1 本のまま（D22 までの設計） | 用途が成立しない。**切って繋ぎ直す道具は使われない** |
| 裏で好きなだけ張る | **これが PRD §4-1 の禁止そのもの。**見えない接続を作らない |
| 人は複数・AI は 1 本 | 面ごとに違う規則を作ると、帯に出る操作の意味がぶれる |

**併せて決めたこと — 接続を維持する**

**黙って切れないようにする。**SSH の keepalive を入れ、一定間隔で相手へ問い合わせる。

- **`exec` でダミーのコマンドを打つ形にはしない。**それは帯に出る操作になり、
  「誰も打っていないコマンド」が並ぶ。**帯は人と AI の操作だけを載せる場所**（PRD §4-2）
- プロトコルの keepalive なら帯に出ない。**出すべきは切れたときだけ**

**これを止めるべき条件**

- タブに出ていない接続が 1 本でも見つかったとき。**そのときは本数の制限へ戻す**
- 開いた本数が増えて、どれが本番か分からなくなったとき。
  **印（色・タグ）をタブにも出す**方へ倒す（本数を減らす方ではない）

**実行状況**

実装済み。実機で 5 本のテスト（2 本同時に開く／宛先が移る／閉じたら残りへ移る／
開いていないものは選べない／**操作は最後に開いたものではなく宛先へ行く**）。
keepalive は 30 秒 × 4 回。`inactivity_timeout` は外した。

## D26 — 画面のキャプチャを MCP に置く。**ただし既定で伏せる**

**決めたこと**

**AI が自分で画面を見て、崩れを見つけられるようにする。**MCP に `capture_window` を置く。

**ただし、既定は「伏せた状態」で撮る。**接続名・タグ・サーバー側のパス・指紋・
ファイル一覧をぼかしてから撮る。伏せないで撮るのは、**人が明示したときだけ**。

**根拠**

- 型検査は崩れを 1 件も止められなかった。**1 日で 3 件出て、3 件とも人が見つけた**
  （クラス名の衝突で幅 3px、割り当て名の誤りでメニューが消える、項目の渡し忘れ）
- 画面を見ずに作ると、**同じことが繰り返される**。人の目を毎回借りるのは持続しない
- 一方で **CLAUDE.md 禁止事項 4** が「スクリーンショットに接続先を写さない」と
  はっきり書いている。**この製品は画面そのものに接続先が写り込む**
- 撮った画像は AI の文脈に入り、記録に残る。**伏せていない画像は、そこから漏れる**

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| キャプチャを作らない | 崩れを見つける手段が人の目しかなくなる。**実際に見逃し続けた** |
| 伏せずに撮る | 禁止事項 4 そのもの。**AI の文脈と記録へ接続先が入る** |
| 撮ったものをリポジトリへ置く | commit history に焼き付く。**出す前しか対策できない**（PRD §8） |
| DOM を読んで文字で確かめる | 重なり・潰れ・はみ出しは**文字では出ない**。実際 `.bar` の 3px は DOM の
  computed width を見て初めて分かった |

**How to apply**

- `redact` の既定は `true`。**省略したら伏せる**
- 伏せるのは画面側（CSS）で行い、**撮る前に伏せ終わっていることを確かめてから**撮る。
  先に撮って後からぼかすと、**元の画像が一瞬でも存在する**
- **撮ったものをリポジトリへ置かない。**`.gitignore` で弾く

**これを止めるべき条件**

- 伏せたはずのものが 1 度でも写ったとき。**そのときはキャプチャごと落とす**
- 「伏せると見えないから」と `redact: false` が常用され始めたとき。
  **伏せ方を直す**方へ倒す（既定を変える方ではない）

**実行状況**

**実装済み**（2026-08-30）。`xcap 0.9`（Apache-2.0 / Windows・macOS 対応）を使う。

- 伏せるのは画面側（`tokens.css` の `[data-redact='on']`）。**塗り潰す**（ぼかしにしない
  — 拡大で読み取られうる）。文字は消えるが**文字の幅と行の高さは残る**
- **伏せ終わったと画面が返してから撮る**（`capture://redact` → `capture://ready`）。
  3 秒待って返事が無ければ**撮らない**。「たぶん伏せ終わっただろう」で撮らない
- 撮影が失敗しても**必ず伏せを解除する**（伏せたままの画面を人に残さない）
- MCP は `redact` を省略できるが、**省略したら伏せる**
- **ファイルに書かない。**MCP の応答として渡すだけ（`.gitignore` の `*.png` は保険）

**確かめたこと**（2026-08-30）:

伏せる前と後で、入力欄・ラベルを含む **17 要素の位置と大きさが 1px も動かない**ことを
実測した。**動いてしまうと崩れが見つからず、作った意味が無い。**

**人にしかできない残り:** macOS の「画面収録」の許可。許すまで
`capture_window` は理由を書いて断る（**黙って失敗しない**）。

## D27 — ダウンロードは**人（GUI）の側にだけ**入れる。MCP には置かない — 【決定・2026-08-30】

**決めたこと**

サーバー → 手元のダウンロードを入れる。**ただし口は GUI だけ。**
MCP に `download` / `download_file` は**置かない**（PRD §4-3 の一覧では未着手のまま残す）。

手元にある同じ名前は**黙って上書きしない**。上書きは人が画面でその都度選んだときだけで、
**1 回ごとに戻る**（押しっぱなしにできない）。落とし先のディレクトリは**勝手に作らない**。

**根拠**

- **D21 が引いた線がここに効く。**AI が書けるローカルは「接続の設定ファイル」だけと
  決めてある。**手元の任意の場所へ書ける口は、その線の外側**であって、
  ダウンロードのついでに広げてよいものではない（product-baseline §15）
- **AI 側は困っていない。**中身が要るなら `read_file` がある。
  `download` が足すのは「**手元のディスクへ書く**」という別の能力だけ
- 囲い（D22）はサーバーを守るもので、**落とす側では 1 ミリも効かない。**
  守る相手が変わるのに、同じ囲いで守れているつもりになるのが一番危ない
- **落とすファイル名を決めるのはサーバー。**一覧はサーバーが返す。
  `../../.ssh/authorized_keys` を返されたまま繋ぐと、**繋いだ相手が手元へ書ける**。
  1 語であることを確かめる関門を、GUI の口に置いた（`safe_local_name`）

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| MCP にも `download` を置く | **D21 の線を、決め直さずに越えることになる。**要るなら決定を先に出す |
| AI の落とし先を「囲いの手元版」で縛る | 囲いをもう 1 種類増やすことになる。**まだ用途が無い**（YAGNI）。要るときに D22 と揃えて設計する |
| 上書きを既定で許す | 落とす側が壊すのは**人の手元のファイル**で、sshboard からは戻せない（§13） |
| 上書きの許しを覚えておく | 「一度承認された操作が、次も承認されているとは限らない」（§13）。**儀式になったゲートは無い方がまし**（D22 で同じ判断をしている） |
| 落とし先のディレクトリを自動で作る | 打ち間違えたパスがそのまま新しいディレクトリになり、**どこへ落ちたか分からなくなる** |

**これを止めるべき条件**

- 「AI に落とさせたい」用途が**実物として**出たとき。
  そのときは**この決定を上書きする決定を書いてから**、手元側の囲いごと設計する。
  実装を先に足さない
- `safe_local_name` を迂回する経路が生えたとき。**落とす口を 1 か所に保てていない**

**実行状況**

実装済み。`Engine::download_file` ＋ `OnConflict`（`crates/sshboard-engine/src/engine.rs`）、
Tauri の `remote_download`（`apps/desktop/src-tauri/src/session_cmd.rs`）、
画面は右のペインで選んで左の現在地へ落とす形。
テストは Rust 8 本（うち実機 3 本）＋ フロント 3 本。
**MCP のツールは 16 本のまま**で、ツール一覧を見張るテストが通っている。

## D28 — 鍵の形式を人に意識させない。**判定は中身で、変換はしない**（D19 を覆す）— 【決定・2026-08-30】

**決めたこと**

**人に鍵の形式を意識させない。**WinSCP が「形式を判定して面倒を引き受ける」のと同じ立場を取る。

1. **判定は中身で行う。拡張子を見ない。**
2. **変換はしない。**`russh` 0.63（`ssh-key` 0.7）が PPK v2 / v3 をそのまま読む。
   **変換すべきものが最初から無い。**
3. 画面は「鍵を選ぶ」だけ。**何形式か・パスフレーズが要るかは製品が言う。**
4. 使えないもの（公開鍵・鍵でないファイル）は**名前を付けて断る。**

**根拠**

- **D19 の前提が事実として誤っていた。**「読める Rust crate が実質無い」と書いたが、
  **既に採用している `russh` が読める**（`src/keys/format/mod.rs:48` で
  `PuTTY-User-Key-File-` を見て `PrivateKey::from_ppk` へ渡している）。
  **依存を 1 つも増やさずに対応できる**
- **拡張子で判定していたのが、二重に害だった**（実測・2026-08-30）:
  - `*.tera.ppk` という名前のファイルの**中身が OpenSSH 秘密鍵**だった。
    製品は「PuTTY 形式です。変換してください」と出し、**要らない puttygen 作業へ送る**
  - 本物の PPK は russh がそのまま読めるのに、**使えないかのように見せていた**
- **パスフレーズの判定が PPK を知らなかった。**`Encryption:` 行を見ていないため
  暗号化された PPK を「素の鍵」と誤判定し、**何も聞かずに認証へ行って失敗**していた。
  実物は 32 本中 26 本がパスフレーズ付きで、**ほぼ全部がこれに当たる**
- 運用者の言葉:「**鍵の型とか、意識するのは面倒くさいし、くだらないタスク**」。
  そのとおりで、これは**製品が引き受けるべき仕事**

**採らなかった案とその理由**

| 案 | 採らなかった理由 |
|---|---|
| D19 のまま（変換手順を案内する） | **前提が誤り。**変換しなくても読める。案内は人に無駄な作業をさせるだけ |
| WinSCP と同じく変換して保存する | **平文の鍵がディスクに残る。**D11（自前の鍵ストアを作らない）と §14 に触る。読めるのに保存する理由が無い |
| `.ppk` を自前で解釈する | D19 の心配は正しい。**自前で解釈しないまま目的を達せる**なら、そちらを採る |
| 拡張子での判定を残したまま中身も見る | 2 つの判定が食い違う。**食い違ったのが今回の事故そのもの**。判定は 1 か所 |
| `puttygen` を呼び出す | 利用者の機械に入っている保証が無い。外部コマンドを増やさない |

**How to apply**

- 判定は `sshboard-ssh` の `inspect_key`（**中身のバイト列だけを受け取る純粋関数**）1 か所。
  画面も Engine もここを通る。**2 つ目の判定を作らない**
- **鍵の中身は通り抜けるだけ。**保持も記録もしない
- 断り文に**鍵のパスを入れない**（パスは接続先の情報・CLAUDE.md 禁止事項 4）。
  出すのは形式の名前だけ
- 読めないファイルは「判定しない」に倒す。**繋ぎに行って正直に失敗させる**方が理由が分かる

**「どんな鍵でも」ではない。実測した範囲**（2026-08-30）

判定が実物と食い違えば製品が嘘をつくので、**`inspect_key` の言い分と
`russh` の実際の挙動を突き合わせるテスト**を置いた（`tests/key_formats_really_load.rs`）。
鍵はテスト中にその場で作って捨てる。

| 形式 | 素 | パスフレーズ付き |
|---|---|---|
| OpenSSH | 使える | 使える |
| PuTTY v2 / v3 | 使える | 使える |
| PEM（PKCS#1） | 使える | AES-128-CBC は使える／**AES-256-CBC は使えない** |
| PKCS#8 | 使える | **使えない** |

**使えない 2 つは、繋ぐ前に断る。**理由は「秘密鍵を指してください」ではなく
**「この暗号方式に対応していません」**として出す（指しているので、前者は的外れ）。

- **暗号化された PKCS#8** — `russh` が復号できない（実測）
- **PKCS#1 の AES-256-CBC** — `russh` の PKCS#5 復号に `Aes256Cbc => unimplemented!()` が在る。
  **人はどんなファイルでも選べるので、渡すとアプリが落ちうる**

**これを止めるべき条件**

- 判定が外れて、**繋がるはずの鍵を断った**とき。そのときは断りを緩め、
  **「分からないものは通して、認証に失敗させる」**方へ倒す（拒否リストにしない）。
  上の突き合わせテストが**過剰な拒否も検出する**（読めるのに断っていたら落ちる）
- `russh` が PPK 対応を落としたとき。**そのときは変換ではなく、依存の選び直しを検討する**
- `russh` が上の 2 つを読めるようになったとき。**拒否を外す**（テストが教えてくれる）

**実行状況**

実装済み。`crates/sshboard-ssh/src/key_file.rs`（判定）、`Engine::auth_for`（パスフレーズの要否と
使えない鍵の拒否）、Tauri の `inspect_key_file`、接続タブの表示と鍵のファイル選択。
テストは Rust 12 本（うち実機 2 本 = **PPK のまま実際に繋がることを確認**）＋ フロント 5 本。
`conn.ppk.*`（変換の案内）は 11 言語すべてから削除した。

## D29 — 端末は人と AI が**共有する**。触っている側以外はロックする（D3 を条件つきで覆す）— 【決定・2026-08-30】

**決めたこと**

**AI にコンソールを渡す。**ただし「渡しっぱなし」にはしない。

1. **同時に触れるのは 1 人**。AI が触っている間、**人側の入力はロックされる**（逆も同じ）
2. **人はいつでも取り返せる。**ロック解除と、**停止**（走っているものを切る）を画面に置く
3. **人には常に見えている。**打っているものも返ってきているものも、その場に出る
4. **MCP に「投げっぱなしの `run_command(cmd)`」は作らない。**渡すのは**対話しているコンソール**であって、
   人の見ていない所で 1 行実行して返る口ではない

**根拠**

- **D3 は初期開発のリスク対策だった**（運用者・2026-08-30）。
  実際に必要なのは「人と AI が**一緒に**コンソールを触れること」で、
  読み取り専用の道具は**主要な用途を満たさない**（D22 のときと同じ構図）
- **D3 が本当に禁じたのは「使わない約束でしか防げない状態」**であって、AI がコマンドを打つこと自体ではない。
  D3 の本文にこうある — 「**約束は手順書であって、ゲートではない**」。
  今回入れるのは約束ではなく**ゲート**:
  - **排他ロック** — 2 人が同時に打ち込んで壊す事故が構造的に起きない
  - **停止ボタン** — 暴走を人がその場で切れる。**押す相手が常に在る**
  - **常時可視** — 人の見ていない所で動かない（PRD §4-2 そのもの）
- **投げっぱなしより、対話している方が安全**という逆転がある。
  `run_command(cmd)` は**返ってきたときには終わっている**。
  対話コンソールは**途中で止められる**
- 排他ロックは**事故の防止でもある。**人と AI が同じ端末へ交互に打つと、
  **どちらの意図でもない文字列**がシェルに入る

**採らなかった案とその理由**

## D31 — 暗号化 PKCS#8 は、**方式まで見て**判定する（D28 の「止めるべき条件」に当たった）— 【決定・2026-09-02】

D28 は「読める → **断ってはいけない**」を止めるべき条件として挙げていた。
**そこに当たった。**初回 push の CI（ubuntu）で発覚した。

### 何が起きていたか

`key_file.rs` は見出しだけを読む方針で、
`-----BEGIN ENCRYPTED PRIVATE KEY-----` を**一律で「使えない」**と判定していた。
根拠は 2026-08-30 の実測だが、**その実測は macOS だけで取られていた。**

`ssh-keygen -m PKCS8` は方式を選べず、**既定が OS で違う。**

| 作った所 | PBKDF2 の PRF | `russh` |
|---|---|---|
| macOS（LibreSSL 3.3.6） | **省略 ＝ hmacWithSHA1** | 読めない |
| Linux / Windows（OpenSSL 3） | **hmacWithSHA256** | **読める** |

つまり **Linux / Windows の ssh-keygen が作る暗号化 PKCS#8 を、
製品はまるごと「使えません」と断っていた。**
Mac 利用者がサーバー側で作った鍵を持ち帰る経路も、同じく塞がっていた。

### 決めたこと

`encryptionAlgorithm`（暗号方式の名前）まで見て分ける。
**暗号文には触れない。**方式の名前は秘密ではない。

**読める組み合わせだけを数え上げる**（`src/pkcs8_cipher.rs`）:

```
PBES2 ＋ aes-128/192/256-cbc ＋（PBKDF2 の PRF が hmacWithSHA256 以上／または scrypt）
```

### 根拠（実測・2026-09-02・`russh` 0.63・16 検体）

| 方式 | 結果 |
|---|---|
| PBES2 / AES-CBC / PRF = SHA256・SHA512 | **読める** |
| PBES2 / AES-CBC / scrypt | **読める** |
| PBES2 / AES-CBC / PRF = SHA1（省略時の既定） | 断られる |
| PBES2 / des-ede3-cbc（PRF によらず） | 断られる |
| PBES1・PKCS#12 PBE（MD5-DES / SHA1-3DES / SHA1-RC2-40） | 断られる |

**PKCS#8 では一度もパニックしない。**必ず `Err` が返る。
PKCS#1 の AES-256-CBC（`unimplemented!()` に落ちる）とはここが違うので、
**「落ちるから先に断る」という理由は PKCS#8 には無かった。**

### 採らなかった案とその理由

| 案 | 理由 |
|---|---|
| 一律で「使える」にし、`russh` に断らせる | D28 の主眼（「使えます」と言って読めないのが最悪）を捨てることになる |
| 落ちたテストを OS 別にする | **実測が macOS 依存だったという本体の誤りが残る。**Linux 利用者の鍵は塞がったまま |
| `pkcs8` crate を足して正式に構文解析する | 依存を 1 つ増やす。**見るのは先頭の OID だけ**で足り、`base64` は既に直接依存にある |

### 分からないものの倒し方

- **方式が分かって、許可リストに無い** → 断る（実測が揃っている）
- **DER が解けず方式が分からない** → **通す。**何も分かっていないので、
  断ると正しい鍵が行き止まりになる。`russh` が理由付きで断ってくれる

### これを止めるべき条件

`russh` が対応を広げたとき。**`tests/key_formats_really_load.rs` が落ちて教える**
（方式を名指しして両側を確かめている）。そのとき許可リストを緩める。**先回りしない。**

### 実行状況

- `crates/sshboard-ssh/src/pkcs8_cipher.rs` を追加（新しい依存なし）
- `key_file.rs` は見出し方針のまま。**例外はここ 1 か所だけ**と明記
- テストを**プラットフォームに依らない形へ**書き直した。
  `openssl pkcs8 -topk8` で方式を名指しし、**読める側／読めない側の両方**を確かめる
- **鍵の実物はリポジトリへ置いていない**（product-baseline §14）。実行時に作って捨てる

## D33 — MCP のポートは **22022 に固定**する（D15 の未決を閉じる）— 【決定・2026-09-02・人】

D15 は「ポート番号の扱いは**まだ決めていない**。…**実際に登録して決める**」で終わっていた。
**Windows の実機で登録してみて、決まった。**決めたのは人。

### 何が起きていたか

`MCP_PORT = 0`（OS に空きを選ばせる）だったため、

- **起動のたびに URL が変わる。**`claude mcp add` を毎回やり直すことになる
- **`.mcp.json` に書けない。**次の起動で番号が変わって壊れる
- そのため GUI は「登録コマンドを毎回コピーする」形になっていた

**合言葉（トークン）は既にファイルで使い回していた**（`resolve_token`）。
その理由（「起動ごとに変わると人が毎回やり直すことになる」）が、
**番号にはそのまま適用されていなかった。**

### 決めたこと

**既定は `22022` 固定。**環境変数 `SSHBOARD_MCP_PORT` で人が動かせる。

**22022 を選んだ理由:**

- SSH の `22` から辿れて覚えやすい
- **Linux（32768〜）と Windows（49152〜）の一時ポート範囲より下。**
  そこに置くと、OS が外向き接続へ割り当てて**ぶつかる日がある**
- 1024 以上なので特権が要らない

### ぶつかったときに、黙って別の番号へ逃げない

**これが要点。**空いている番号を勝手に探して立つと、

- 人は `.mcp.json` に書いた番号で待っている
- 実際は別の番号で立っている
- **どちらも「動いている」ように見えて、繋がらない**

なので **立ち上がらなかったら、立ち上がらなかったと言う。**
番号を添えて画面へ出す（`mcp://failed` イベント ＋ `mcp.failed` の文言）。
**以前は `eprintln!` して黙って戻っており、画面は「起動中」のまま止まっていた。**

環境変数の値が読めないときも同じで、**黙って既定へ倒さず、理由を出してから**倒す。

### 採らなかった案とその理由

| 案 | 理由 |
|---|---|
| 実際の番号を設定ファイルへ書き出す（D15 の代案） | **読む側が要る。**`.mcp.json` は静的なので、結局人が毎回写す |
| ぶつかったら次の空き番号へ | **静かに繋がらなくなる。**上記のとおり |
| 一時ポート範囲（49152〜）から選ぶ | **OS に取られる。**「今日はなぜか起動しない」が出る |

### これを止めるべき条件

**22022 が実際にぶつかる報告が出たとき。**そのときは既定を変えるのではなく、
まず `SSHBOARD_MCP_PORT` で回避してもらい、**頻度を見てから**既定を動かす。
既定を動かすと、既に `.mcp.json` を書いた人が全員壊れる。

### 実行状況

- テスト 6 本（既定が 0 でないこと・一時ポート範囲より下であること・

| **更新署名**（minisign） | **配布元が本物か。**改竄した更新を入れさせない | 無料 | **入れた（D34）** |
| コード署名（Authenticode / Apple） | OS の警告が出るかどうか | 年 5.5 万円 / 99 ドル | **入れない**（D12 のまま） |

**更新署名は Tauri が必ず検証します。**検証できない更新はそもそも受け取りません。
つまり「未署名アプリだが、更新経路は暗号的に守られている」状態になります。

**鍵は人が作りました**（product-baseline §14 — AI は秘密情報を作らない・置かない）。
公開鍵は `tauri.conf.json` に、秘密鍵とパスワードは GitHub Secrets に。

> **秘密鍵を失うと、既に入っている版へ更新を配れなくなります。**
> 利用者は入れ直しになります。

### 宛先は固定タグに置く

**`releases/latest` は prerelease を含みません。**α は prerelease で出す（D30）ので、
そこを指すと更新が永久に見つかりません。

**`updater` という固定タグの Release に `latest.json` だけを置き、毎回差し替えます。**
アプリに焼き込む URL は変えられないので、宛先は 1 つに固定する必要があります。

### 目録の version は「アプリが名乗る番号」でなければならない

**ここで 1 回間違えました。**タグ（`v0.1.1-alpha.2`）をそのまま入れると、
semver では `0.1.1-alpha.2` < `0.1.1` なので、**0.1.1 を名乗るアプリからは
「古い版」に見えて、更新が永久に来ません。**

目録は `tauri.conf.json` の番号を使います。そのうえで
**タグの数値部分とアプリの番号が違ったら、Release を作らずに止めます。**

**結果として「1 リリース ＝ 1 回のバージョン上げ」になります。**
同じ `0.1.1` のまま alpha.2 → alpha.3 と出しても、更新は届きません。
`sh tools/bump-version.sh` を必ず通すこと。

### 黙って失敗させない所

- **鍵が無ければビルドの前に落とす。**署名の無い成果物を静かに出すと、
  目録が作れず更新が届かない
- **`.sig` が 1 つも無ければ Release を作らない**
- **目録に載せるものが 1 つも無ければ止める**
- 更新に失敗したら**画面に理由を出す**（繋がらないのか、署名が合わないのかで次の一手が違う）

### いま載るのは 2 つだけ

`windows-x86_64` と `darwin-aarch64`。**Intel Mac は載りません**（CI が arm64 のため）。
要望が出たらランナーを足します。**「載っていない」ことを黙らないよう、
目録が空なら止める形にしてあります。**

### これを止めるべき条件

**更新が原因で壊れた版が配られたとき。**そのときは `updater` タグの目録を
1 つ前の版へ戻せば、その場で止まります（アプリ側の変更は要りません）。
