# 002. 稼働中サーバーへ実際に SSH で繋ぐ（Phase 0）

## なぜ

対象は**従来型のレンタルサーバー / VPS で動き続けているサービス**です（PRD §0-3）。
新しい環境ではないので、**古い鍵交換方式・暗号方式が残っている可能性があります。**
ここで繋がらないと、あとの全部が机上になります。

**カタログを読んで判断しない。実機に繋ぐ。**

## やること

- 実際に保守している稼働中サーバーへ接続する（read-only な操作しかしない）
- 繋がらなかった場合、**何が原因で・どの設定を足せば繋がるか**まで確認する
- `sftp` サブシステムと `exec` の両方を、**同じ 1 本の接続の上で**使えることを見る

## 完了条件

- [ ] 対象サーバーへ接続し、`ls` 相当（sftp）と `echo` 相当（exec）が両方通った
- [ ] 上を **1 本の SSH セッションの上で** 行った（2 本張っていない）
- [ ] 繋がらなかった方式があれば、その方式名と回避策を `.claude/decisions.md` に書いた

## やらないこと

- **接続先のホスト名 / IP / ユーザー名を、リポジトリのどこにも書かない**（PRD §8）。
  記録するのは「繋がったか」「どの方式か」だけ
- 書き込み操作をしない

### 追加の確認項目 — 漢字コード

**当初の完了条件に入っていませんでした。足します。**

- `xterm.js` は UTF-8 前提です（D7）
- **端末だけの問題ではありません。**`read_file` で AI に渡す文字列も同じです。

繋いだときに、`locale` と、実際のログ / 設定ファイルの中身のバイト列を見てください。
UTF-8 でなかった場合、変換をどこに置くか（Operation Engine か、面ごとか）が
D7 の前提に関わります。

## ここで出た、設計に関わる問題 3 つ

### 1. `/var/log` がログインユーザーで読めない — **主用途に直撃します**

```
/var/log/cron    → Permission denied
/var/log/maillog → Permission denied
```

PRD §0-2 の主用途は「障害時のサーバ調査 ＝ ログを読む」で、
Phase 1 では **sudo を渡さない**と決めています（PRD §5 / D2）。
**このままだと `read_log` が主用途で機能しません。**

**未解決。**人へ確認すること: **実際に読みたいログはどこにあるか。**
アプリ自身のログ（`~/` 配下や `/var/www/.../logs`）なら読めるはず。
そこが分かるまで `read_log` の設計を決めない。

### 2. 手元の鍵が `.ppk`（PuTTY 形式）だった — **副ユーザー要件に直撃します**

保守に使っている鍵は Tera Term / WinSCP 用の `.ppk` でした。
**OpenSSH 系（russh も ssh2 も）は `.ppk` を読めません。**
`puttygen` で変換するか、`.ppk` を自前で読む必要があります
（**読める Rust crate は実質ありません**。2026-08-27 時点で確認）。

PRD §1 の副ユーザーは「Tera Term / WinSCP の使い勝手から離れない」ことが要件です。
**その人たちの鍵は `.ppk` で手元にあります。**読めないと鍵を作り直させることになります。

**未決。**下記のどれかを人が決める:

| | 内容 | 代償 |
|---|---|---|
| A | 何もしない。OpenSSH 形式の鍵を使ってもらう | 既存利用者に鍵の作り直しか変換を強いる |
| B | 登録時に `.ppk` を検出し、**変換手順を画面で案内する** | 実装は小さい。人の手は 1 回要る |
| C | `.ppk` を自前で読む | 実装が増える。鍵の形式を自前で解釈するのは事故のもと |

### 3. ライブラリによってホスト鍵の指紋が違って見える

同じサーバーに対して、russh と ssh2 で**別の指紋**が返りました。
**すり替えではありません。**成立したホスト鍵の方式が違うためです
（ssh2 は `ecdsa-sha2-nistp256` を選び、russh は別の方式を選んだ）。

**指紋を固定するときは、方式も一緒に記録すること。**
方式を書かずに指紋だけ固定すると、「同じサーバーなのに一致しない」が起きます。
